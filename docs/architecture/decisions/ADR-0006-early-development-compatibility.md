# ADR-0006: No speculative backward compatibility during early development

- **Status:** Accepted (product-owner decision)
- **Context:** The Factory is pre-release and has no declared stable external APIs, durable production data or supported third-party clients. Keeping aliases, adapters, dual paths and obsolete schemas for hypothetical consumers would compound design debt and slow iteration.
- **Decision:** Internal contracts may change incompatibly while in F0/F1 and later explicitly designated experimental phases. Prefer the simplest correct interface. Remove obsolete code, compatibility layers, old test fixtures and duplicated migration paths; update all in-repository consumers, examples, docs and verification cases together in the same change. Do **not** require backward compatibility with an unshipped interface solely because it existed in an earlier draft.
- **Boundaries:** This rule does not permit data loss, destruction of audit/evidence history, weakening of security or the Quality Baseline, secret disclosure or unilateral changes to agreed protocol authority. Once an API, persisted-data format, plugin interface or user contract is explicitly marked stable/published, breaking it requires a separate versioning/migration decision and the applicable approval. Repositories beyond the Factory's control and actual external consumers must be assessed rather than assumed nonexistent.
- **Consequences:** Faster and cleaner iteration, fewer ghost contracts. Changes may require coordinated refactors and replacement of disposable development data or fixtures; any necessary data reset must be authorized, documented and restricted to explicitly disposable environments.
