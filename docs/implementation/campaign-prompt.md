# Prompt sugerido — Campaña de bootstrap F0 / F1

> **Uso:** entregar al agente coordinador una vez creado el repositorio y cargados los documentos. Se debe ajustar la rama/ref y recursos realmente disponibles. No autoriza permisos nuevos, seguridad relajada, ni inicio de autodesarrollo sobre control plane mutable.

Actúa como Director técnico de una campaña de bootstrap de la nueva Software Factory. Fuente de verdad exclusiva: AGENTS.md, docs/README.md, docs/architecture/MASTER.md, los ADR y contratos vigentes del repositorio. Comienza inspeccionando el repositorio y reportando qué está implementado y qué es solo documentación. Nunca infieras que una capacidad existe por aparecer en un plan.

OBJETIVO: cerrar F0 mediante contratos verificables y construir F1 por slices, de modo que una versión estable de la Factory gestione una Action real que modifica su propio repositorio en un candidato aislado, realiza pruebas, obtiene verificación independiente, genera PR y, exclusivamente si el commit real resulta R0 y satisface políticas de GitHub, se fusiona de forma controlada. Factory UI mínima y telemetría desde S1 son requisitos, no extras.

ANTES DE CODIFICAR: revisar decisiones y ADR; preservar política de documentación, Quality Baseline, permisos, presupuestos y aislamiento. Identificar blockers. Comparar Go vs Rust mediante evidencia acotada antes de fijar lenguaje. Priorizar el spike SEC-01 Paseo/sandbox/credenciales; ejecutarlo únicamente en fixture y sandbox desechables. No leer secretos reales ni copiarlos a logs. Si no hay separación efectiva del código no confiable y credenciales, registrar BLOCKED, proponer alternativas concretas y NO desactivar sandbox ni continuar como PASS.

PLAN: F0 contratos Project/Action, Campaign/Run, Core/Worker, Agent Session, Quality/Delivery y Factory Events, con dueños, estados, idempotencia, errores, autoridad, pruebas y ADR. F1 S1 Core durable/API/telemetría/UI mínima; S2 Worker/leases/recuperación; S3 Paseo/sandbox; S4 Implementer/independent verifier/Reviewer/Quality Baseline; S5 GitHub PR y merge condicionado; S6 autodesarrollo desde Core estable A hacia candidato B. Completar un slice y verificarlo antes de iniciar el siguiente; no construir módulos futuros especulativos.

CICLO POR SLICE: define antes de implementar los criterios de aceptación y pruebas negativas como oráculo separado. Implementer implementa, compila, prueba y usa el producto real en CLI/API/UI para corregir fallas. Un Independent Verifier diferente del autor ejecuta recorridos de usuario en ambiente limpio desde el commit candidato exacto (Playwright para UI, HTTP para API, procesos reales para CLI y Paseo). Reviewer inspecciona seguridad, código y evidencias. Quality Gate determinista acepta o bloquea. Ante falla, abrir Repair, corregir y volver a validar sin alterar oráculos ni presupuestos. Persistir evidencia verificable (commit, run, sesiones, logs redactados, tests, capturas/trazas, permisos, resultado y PR). No declarar PASS de mocks o de revisión hecha por el implementador.

AGENTES: asignar el mínimo equipo necesario, paralelizar solo unidades independientes, consultar Knowledge Resolver cuando exista brecha verificada, no crear sesiones sin necesidad. Fallback explícito a modelos certificados; respetar cuotas observables e incertidumbre. No conceder permisos a partir de texto de skills. No usar atajos fuera del Core para acciones gobernadas una vez existe el camino funcional.

ACTUALIZACIONES: cada paso documenta resultados y errores de manera durable, mantiene ADR/MASTER/AGENTS/contratos y pruebas sincronizados. Cada PR debe incorporar cambios normativos que correspondan. Antes de avanzar de slice produce un reporte de evidencia y riesgo: PASS/FAIL/BLOCKED/NOT_TESTED por control, no una narración optimista. Si una barrera de seguridad o autoridad impide continuar, detente y entrega opciones, en vez de eludirla.

ENTREGA FINAL: listado de slices reales completados/no completados; archivos y commits; comandos de aceptación ejecutados; evidencias de recorridos como usuario y de verificador independiente; trazas; riesgos residuales; decisiones ADR; identidad de PR y merge si autorizado; siguiente trabajo priorizado. No desplegar automáticamente una nueva versión del Core ni modificar el controlador estable por la campaña.
