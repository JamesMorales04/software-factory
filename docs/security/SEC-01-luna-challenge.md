# SEC-01 Hybrid D/A adversarial challenge

**Disposition: FAIL.** D/A is a useful isolation substrate proposal, but the credential topology and acceptance rule do not establish safe credential-bearing execution. SEC-01 remains BLOCKED.

## Blocking findings

1. **M4 relocates authority; it does not remove it.** Validation §5 defines a proxy that holds keys while the container sees an endpoint, then calls M4+M5 the strongest OpenCode path. Any workload able to call that endpoint can ask the proxy to exercise the credentialed API and return the result. If it is a transparent forwarder, it is a confused deputy: endpoint reachability is authority. Short-lived/spend-limited credentials bound duration/cost, not operation scope or data disclosure. No operation-level policy, caller binding, replay control, or data-flow constraint is specified (`SEC-01-validation.md:70-82, 133-151`; report `:86-91`). The proxy is undesigned (`SEC-01-validation.md:38-40, 122-123`). **Must specify and test proxy authorization semantics; otherwise M4 cannot be counted as custody protection.**

2. **§6 decision rule is not sufficient/falsifiable for the claimed property.** It declares whole-runtime “SUFFICIENT” if routes deny synthetic canary reads and the dev task succeeds (`SEC-01-validation.md:90-106`). That only tests confidentiality via listed read paths. A tool can submit workspace/source/canary data in a syntactically legitimate provider API request, package fetch, or other allowed egress; no canary needs to appear in tool output. §6's sinkhole probe is not a success/fail condition in the decision rule, and a sinkhole cannot represent the real provider API's legitimate semantics. Passing therefore leaves credential misuse/exfiltration open. Its “every native route” universe is not fixed: Codex already has local MCP without shell sandbox, remote MCP with no sandbox, and weaker resume overrides (`/tmp/sec01-codex-findings.md`, opening disposition and CLI/MCP/resume sections); §6 omits remote MCP and treats all routes as enumerable. **Blocking:** no sound inference from this test to credential safety.

3. **Credential topology is internally inconsistent for Codex.** Report says credentials never enter container and proposes “scoped short-lived delivery” with `inherit none` plus auth-path hiding (`SEC-01-redesign-report.md:21-29`), while validation says M2 hides the auth file but provider control plane reads it directly, and explicitly lists local-MCP, remote-MCP, resume gaps (`SEC-01-validation.md:71-82`). Same-UID provider and tools in the whole-runtime model mean M2 shell denials do not prove the provider cannot exercise its own credential through an unconfined route. The plan needs to state exactly where key material resides and which principal can invoke it; “provider control plane” is not shown isolated from model-reachable behavior. Container has no host secrets, but that only answers host-store reachability, not the delivered/loaded provider credential authority.

4. **Paseo dependency is understated and the gated test may be impossible under current surface.** The stream-A investigation says mandatory immutable policy on agent creation/resume and controlled provider launch are Paseo changes; hooks are mutable optional transforms, and current launchers lack UID/mount/network isolation (`SEC-01-streamA-paseo-surface.md`, PASEO-NEEDS-CHANGE; PASEO-BLOCKED). It also identifies ACP host filesystem/terminal callbacks. Yet report says no Paseo fork needed and calls session→container binding/resume freeze “minimal” hardening (`SEC-01-redesign-report.md:69-82, 215-219`), while validation requires a real Paseo SDK session through the profile (`SEC-01-validation.md:183-191`) and says no session wiring until after §H (`SEC-01-redesign-report.md:169-174`). Without a trusted external launcher that owns every provider process and prevents Paseo/worker fallback, session binding and resume freeze are prerequisites, not later hardening. If Paseo never cooperates, D/A only covers an independently managed process prototype, not the claimed Paseo execution path.

## Additional material gaps

5. **OpenCode M4 hides, rather than closes, its own bypass surface.** OpenCode has host-process plugins/custom tools, shell command expansion, local MCP, and subagents whose agent restrictions may exceed the parent; these execute under the OpenCode process authority (`/tmp/sec01-opencode-findings.md`, “MCP mediation exclusivity” and “Topology”). M4 only changes provider API routing. It does not sandbox those tools or prove all API calls use the proxy; config/endpoint overrides could restore a direct provider endpoint unless immutable policy blocks them. “M4+M5, disabled until certified” is honest only if disabled means no launch/route at the trusted Core boundary, across resume/config/plugin/custom-tool surfaces—not a UI/tool hide. Validation acknowledges proxy as a path but does not enumerate these controls (`SEC-01-validation.md:71-82, 143-150`).

6. **Paseo route closure needs more than the §8 route list.** Validation matrix calls for every enabled route, but §6 enumerates shell, patch, local MCP, subagent, background only (`SEC-01-validation.md:94-103`). Stream A records ACP callbacks, plugins/transforms, provider registration, launch configuration, and possible custom-provider routes (`SEC-01-streamA-paseo-surface.md`, PASEO-SUPPORTS / NEEDS-CHANGE). Unless explicitly disabled or included, “all routes” is not operationally bounded.

7. **Measurement wording is partly corrected, not fully.** Validation §3 carefully limits 140 ms to two `podman run ... true` samples and disclaims session/toolchain/pull timing (`SEC-01-validation.md:3-18`), but report still says D/A is the “ONLY option” passing engineering benchmark and isolation probes simultaneously across providers (`SEC-01-redesign-report.md:36-42), despite OpenCode excluded, dev-image/toolchains/proxy/auth untested (`report:117-126`) and report's own table still labels capability “FULL (proven)” (`report:46-54`). “Loopback allowed/functional” is demonstrated for one synthetic local fetch with `--network=none`, not general loopback safety (`validation.md:10-12`; report `:108-115`). The 140ms figure remains in comparison as performance evidence although it excludes image pull and session startup (`report:52-54`; `validation.md:5-8`). These are scope overclaims, not evidence of exploitable isolation by themselves.

8. **PR #4 KEEP/ADAPT needs a security gate.** Keeping `--exec-mode local` as an explicit alternative risks a caller-selected host path unless the Core authorizes it as TRUSTED LOCAL with scope, expiry, audit and no agent-controlled flag forwarding; the plan lists the flag as KEEP but does not bind it to that authorization (`SEC-01-validation.md:112-129`; report `:98-104,153-167`). ADAPT to proxy env and allowlisted provider endpoints widens network authority: domain allowlisting alone does not constrain API operations or prevent use of permitted endpoints as an exfil channel (`validation.md:29-40`). Also, replacing the universal broker assumption before proxy/custody/provider rows pass can promote an uncertified STANDARD profile; PR #4 should remain infrastructure-only/disabled by default until Core enforces per-row certification (`report:169-174,178-193`).

9. **Single strongest practical failure mode:** the provider and untrusted tools share one execution authority, while the credential proxy/provider endpoint intentionally accepts requests from that authority. An agent can misuse allowed API capability or encode data in legitimate requests without ever reading a credential file; filesystem canaries and tool-output denial oracles will miss it. The architecture needs a policy-enforcing deputy boundary or a demonstrated provider contract that makes such use acceptably scoped.

Residual risks even after repair: provider/API semantic abuse, endpoint/config bypass, complete Paseo route closure (resume, ACP, plugins, MCP, subagents), proxy allowlist correctness, and exact candidate-bound real-session evidence. No authenticated or adversarial tests were performed in this review.
CHALLENGE-FAIL (blocking hole: M4 exposes credentialed API authority to the untrusted runtime without a specified policy boundary, and §6 can pass while that authority is used for exfiltration).
