## PASEO-SUPPORTS

- **Optional MCP path, not exclusivity.** SDK 0.11.4 `protocol/dist/agent-types.d.ts:440-464` exposes `toolPolicy.preapproved` only for MCP tool refs, plus `mcpServers`. These are provider configuration/approval routing, **advisory relative to OS isolation**. Prior recorded D3-D1 proved one host Paseo → Codex → MCP → Podman call, while expressly finding native tools remain available (`docs/security/SEC-01-results-2026-10-18.md:40-46,75-84`).
- **Provider launch configuration.** SDK 0.11.4 `protocol/dist/provider-config.d.ts:12-24` exposes command/env/disallowedTools. Command/env select or configure the child; `disallowedTools` hides/routes provider tools and is **advisory**, not an OS boundary. The 0.11.4 `AgentSessionConfig` has no sandbox, UID, mount, or network field (`agent-types.d.ts:449-470`).
- **Plugin package and capabilities.** 0.9.1 `plugin/dist/server/contracts.d.ts:23-28` permits settings, plugin RPC handlers, provider registration, lifecycle hooks. `plugin/dist/server/lifecycle.d.ts:44-90` gives turn/permission notifications and `before` transforms for agent create/session open/workspace create; `server/dist/server/plugins/lifecycle/index.js:5-32` validates exactly those names. `server/dist/server/agent/agent-manager.js:663-672,3634-3644` applies transforms to config/env. These are trusted daemon-side extension points, **not mandatory tool interception**. A trusted plugin can alter launch config/env and may weaken an intended policy if allowed to transform it; permissions hooks are notifications, not a universal pre-execution veto. `plugin/dist/server/provider.d.ts:6-34,58-71` permits an entire custom provider implementation; `plugin/dist/server/acp.d.ts:11-17,101-110` supplies an ACP provider helper with a command or connector and presentation transformers. That is a potential custom-provider route, not a proven complete external executor.
- **Plugin RPC, not arbitrary native HTTP routes.** `plugin/dist/server/contracts.d.ts:23-28` exposes `handle(contract, handler)`; `server/dist/server/plugins/plugin-process.js:57-73,194-214` registers named RPC handlers/providers/hooks in a separate plugin process. No native route registration appears in that public server context. This is a scoped API conclusion, not a claim that trusted arbitrary Node plugin code is sandboxed.
- **Relay is transport.** 0.9.1 `relay/dist/types.d.ts:1-9` says server/client WebSockets are forwarded bidirectionally without modification; `relay/dist/encrypted-channel.js:1-7` adds E2EE; `relay/dist/cutover-proxy.js:1-9` forwards HTTP to an origin. No tool executor interface appears in these surfaces. Transport encryption is **not OS enforcement** for tools.
- **ACP client callbacks are a partial mediation point.** The ACP adapter handles `readTextFile`, `writeTextFile`, `createTerminal` (`server/dist/server/agent/providers/acp-agent.js:1733-1761`), while `tool_call` updates are converted to timeline events (`:1968-1977`) and permission requests to prompts (`:1629-1664`). Thus ACP has client-side file/terminal callbacks that could be redirected, but its general provider tool calls are executed by the ACP provider process; timeline/permission observation is not a universal executor.

## PASEO-NEEDS-CHANGE

- **Mandatory fail-closed execution policy at agent creation/resume.** Add an immutable, Core-authorized execution profile bound to candidate/run; reject missing or downgraded profiles. The existing plugin `before` hooks are mutable optional transforms (`agent-manager.js:663-672,3634-3644`), so they cannot alone certify enforcement. File-level seam: `server/dist/server/agent/agent-manager.js` `prepareSessionConfig`/`createAgentInternal`/session-open path; protocol session config schema; provider registration policy. No code change was made.
- **Launch providers in a controlled OS context, or replace providers with restricted implementations.** 0.9.1 Codex `server/dist/server/agent/providers/codex-app-server-agent.js:5659-5693` calls `spawnProcess(..., "app-server")`; OpenCode `server/dist/server/agent/providers/opencode/server-manager.js:208-233` calls `spawnServerProcess(..., "serve", "--port", ...)`; `server/dist/server/utils/spawn.js:19-36` uses Node `child_process.spawn` with environment and no UID/mount/network isolation options. ACP provider launch likewise uses `spawnProcess` (`acp-agent.js:738-747,1821-1840`). Narrow Paseo changes would replace these launcher seams with a fail-closed launcher/transport whose process placement is externally enforced. A command override alone can start a wrapper but does not remove native fallback or prove every provider subprocess stays confined.
- **Redirect or disable ACP host callbacks.** `acp-agent.js:1733-1761` currently reads/writes paths with daemon `fs` and starts a native child for `createTerminal`. These must call a disposable Worker broker with scoped capability and no host fallback, or be disabled for the secured profile. The probe callbacks at `:800-820` also need review for credential-bearing discovery.
- **Separate provider credentials from untrusted execution at the OS boundary.** Lead evidence (2026-10-19) observed daemon 0.9.1 pid 4026, worker 4037, with Codex app-server and OpenCode serve as same-UID worker children. Source launch functions above support ordinary child-process inheritance; exact live mounts/UID are lead observation, not established by this source reading. If the credentialed provider executes native tools internally, an S2-Worker broker offered as MCP cannot make all calls mandatory. An OS-enforced credential split plus provider-native tool disabling/delegation is required.
- **Plugin policy surface needs trust control.** Trusted plugins can register providers and transform config/env (`plugin-process.js:74-90,204-210`; `lifecycle.d.ts:78-90`). For a secured profile, disable unreviewed plugins or freeze/validate effective policy after hooks; plugin RPC must not become a privileged alternate effect path. Plugin APIs show no per-tool mandatory hook.

## PASEO-BLOCKED

- **No source proof of every native tool interception.** For Codex app-server and OpenCode serve, the adapter launches the provider and observes protocol events. A guarantee that *every* model tool call goes through a disposable Podman Worker, with no native fallback, requires supported provider-native delegation/disable controls proven for each provider, or a provider fork/change. Paseo's plugin, relay, MCP preapproval, ACP timeline events, and `disallowedTools` cannot by themselves guarantee it. The exact provider-internal tool executor and bypass behavior remain unverified here.
- **Real-auth test is approval gated and was not run.** Current repository status is SEC-01 paused/blocked, with credential-bearing F1-S3 prohibited (`docs/security/SEC-01-results-2026-10-18.md:84-88`). To resume, obtain explicit product-owner authorization for a frozen SEC-01 Action/spec, isolated fixture, approved paths/risk/budget and independent verifier. Then implement a rootless, unprivileged topology with credential custody apart from every untrusted tool path; run a real authenticated Paseo SDK agent through it for each enabled provider/runtime; prove useful scoped edits/tests and fail-closed native alternatives using synthetic host/project/credential canaries and OS/process/mount/UID/network evidence; test egress, cancel/restart/orphans, lease fencing and replay; pin image digests and provider/SDK binaries, redact and bind evidence to candidate IDs, and independently review before any PASS (`docs/security/SEC-01-results-2026-10-18.md:91-97`). No privileged container or real credential file inspection is part of this investigation.

Disposition: **source investigation completed with timeline access unavailable; SEC-01 remains BLOCKED, NOT CERTIFIED.**
